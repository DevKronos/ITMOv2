# Рефлексия

В этой лабораторной работе я попробовал два подхода к разработке по спецификациям: OpenSpec и GitHub Spec Kit. На практике оказалось, что спецификации полезны не только для описания будущей функциональности, но и для обнаружения проблем ещё до написания кода.

Особенно это проявилось при согласовании UI и логики второй фичи. Например, изначально не был предусмотрен случай, когда пользователь открывает страницу с одним городом, а затем меняет город в другой вкладке. В результате кнопка могла бы отметить прочитанными уведомления уже другого города. Чтобы избежать этого, пришлось добавить проверку города и выполнять её в одной транзакции с обновлением уведомлений. Также заранее определили, какие уведомления учитывать, что возвращать при повторном нажатии и как обрабатывать ошибки.

При реализации тоже возникла небольшая проблема: оказалось, что FastAPI возвращает ошибку 422 при отправке пустого обязательного поля формы. Это поведение отличалось от первоначальных ожиданий, поэтому пришлось уточнить спецификации и тесты. Получается, что даже хорошо составленные требования не отменяют необходимости проверять, как всё работает на самом деле.

Из двух инструментов OpenSpec показался более удобным для небольших изменений. В нём проще описать требования, реализовать фичу и затем зафиксировать результат. Spec Kit требует больше документации, зато позволяет подробнее проработать взаимодействие разных частей приложения. Для второй фичи это оказалось полезным.

В целом SDD делает процесс разработки более предсказуемым: заранее понятнее, что именно нужно реализовать и как проверить результат. Главный недостаток — количество документации, которое для небольших задач иногда кажется чрезмерным. Тем не менее работа показала, что предварительное согласование требований может помочь избежать ошибок, которые иначе обнаружились бы уже после реализации.
