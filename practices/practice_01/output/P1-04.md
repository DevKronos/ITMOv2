Findings (ordered by severity)

1. app/api.py, create_review — unvalidated access to payload["diff"] leads to KeyError and likely 500 if the field is missing.
   - Evidence: In the diff, the endpoint directly does `payload["diff"]` without checks (app/api.py lines 35–38).
   - Context: The “Хороший пример” explicitly calls out this risk (“обращение payload["diff"] вызывает KeyError…”, practices/practice_01/context.md lines 49–52). The problem statement also notes the KeyError/500 risk (practices/practice_01/problem.md line 9).

2. app/api.py — no input size guard; diff > 20 000 characters should return HTTP 413 but is not enforced.
   - Evidence: The new endpoint simply forwards `payload["diff"]` to the service; there is no size check anywhere in the added code (app/api.py lines 35–38).
   - Context: Constraint requires rejecting diffs longer than 20 000 characters with 413 (practices/practice_01/context.md line 41). The problem notes the absence of this limit in the API code (practices/practice_01/problem.md line 9).

3. app/review_service.py and app/api.py — response contract mismatch with the target structured format.
   - Evidence: The service returns `{"comment": answer}` (app/review_service.py lines 19–22), and the API returns that dict unchanged (app/api.py lines 35–38).
   - Context: Target result must be `summary`, `risks` (≤3, with `file,line,evidence,risk`), and `checks` (practices/practice_01/context.md lines 29–33). Current implementation returns `{"comment": "<строка>"}`, explicitly marked as a divergence (practices/practice_01/context.md lines 21 and 33; practices/practice_01/problem.md lines 9–10, 27).

4. app/review_service.py / app/api.py — no handling of LLM timeout (10 seconds) and no mapping to a controlled error response.
   - Evidence: `llm.generate(prompt)` is called synchronously with no timeout or error handling paths (app/review_service.py lines 20–22), and the API doesn’t catch or transform errors (app/api.py lines 35–38).
   - Context: Constraints require a 10-second timeout and controlled error responses (practices/practice_01/context.md line 42). The problem points out the absence of explicit timeout handling (practices/practice_01/problem.md line 9). Metrics also target controlled timeout behavior (practices/practice_01/problem.md line 22).

5. Logging constraints are not met: request_id, duration, and status should be logged; content of diff and model output should not be logged.
   - Evidence: The PR adds the endpoint and service call but no logging (app/api.py lines 35–38; app/review_service.py lines 19–22).
   - Context: Logging requirements are specified (practices/practice_01/context.md line 43). Current code does not implement them.

6. Prompt does not lead toward the target structured format.
   - Evidence: The prompt is `"Review this pull request and find problems:\n{diff}"` (app/review_service.py line 20), which is unlikely to produce `summary/risks/checks`.
   - Context: The target format is structured (practices/practice_01/context.md lines 29–33). The current prompt is documented as the AS IS behavior (practices/practice_01/context.md line 21), and remains misaligned with the target contract (practices/practice_01/problem.md lines 9–10, 27).

7. Input type validation is absent.
   - Evidence: The API type-hints `payload: dict` and directly uses it without checking that `diff` is a string (app/api.py lines 35–38).
   - Context: API expects JSON `{"diff": "<строка diff>"}` (practices/practice_01/context.md line 28). The error format for wrong type is currently unknown (practices/practice_01/context.md lines 63–64), but absence of validation is a documented current problem (practices/practice_01/problem.md line 9).

Open questions (from the provided context)
- Should this PR move the API to the target structured contract now, or is that deferred to the next increment? (practices/practice_01/context.md line 65)
- What exact status code and error body should be returned when `diff` is missing or of the wrong type? (practices/practice_01/context.md lines 63–64)
- What is the format of the controlled response for LLM timeouts or internal errors? (practices/practice_01/context.md line 64)

Change summary
- Add input validation for presence and type of `diff` to prevent KeyError and 500s; define controlled 4xx error responses per the team’s decision.
- Enforce the 20 000-character limit with HTTP 413.
- Implement LLM timeout (10 seconds) and map timeouts/errors to controlled responses.
- Align the response to the target structured format (`summary`, `risks` ≤ 3 with fields, `checks`) once the team confirms scope for this increment.
- Add minimal logging for request_id, duration, and status, without logging diff content or model output.
