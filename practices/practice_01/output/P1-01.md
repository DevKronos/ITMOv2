# P1-01: Baseline-ревью TRAINING_PR.diff

Запрос

Посмотри PR в @practices/practice_01/TRAINING_PR.diff и найди ошибки

Ответ

Ниже — обзор проблем по PR, упорядочено по серьёзности, с привязкой к строкам диффа.

Высокая серьезность
1. Отсутствует валидация входных данных и корректная обработка ошибок ввода (app/api.py:35-38). Доступ к payload["diff"] без проверки приведёт к KeyError и 500, вместо ожидаемого 422 от FastAPI при некорректном теле запроса. Рекомендация: описать тело запроса через Pydantic-модель (например, ReviewRequest(BaseModel) с полем diff: str) и указать response_model для ответа.
2. Потенциальная блокировка запроса долгим/IO-вызовом LLM (app/api.py:35-38, app/review_service.py:19-22). Синхронный эндпоинт вызывает потенциально долгую операцию llm.generate(). Это может деградировать производительность под нагрузкой. Рекомендация: сделать обработчик async и вызывать блокирующий код через run_in_threadpool, либо использовать асинхронный клиент LLM.
3. Отсутствие обработки ошибок LLM (app/review_service.py:19-22 и app/api.py:35-38). Любая ошибка/таймаут в llm.generate приведёт к 500 без понятного ответа клиенту. Рекомендация: перехватывать исключения, отдавать 4xx/5xx с объяснением и/или кодом ошибки, логировать подробности.

Средняя серьезность
4. Неопределённый контракт API и OpenAPI-схема ответа (app/api.py:35-38). Типизация dict[str, str] не формирует явную схему в документации, ключ "comment" не закреплён контрактом. Рекомендация: задать response_model (например, Pydantic-модель с полем comment: str).
5. Отсутствие аутентификации/авторизации на эндпоинте создания обзора (app/api.py:35). Если сервис публичный/внутренний — требуется явное решение. Риск злоупотребления и накрутки стоимости LLM.
6. Отсутствуют ограничения и санитайзинг входного diff (app/review_service.py:19-21, app/api.py:35-38). Большие diff могут превышать контекст LLM или лимиты провайдера. Рекомендация: лимит размера входа, усечение/сэмплирование, предупреждение клиенту.
7. Жёсткая привязка к Python 3.9+ через dict[str, str] (оба файла). Если окружение <3.9 — упадёт. Рекомендация: либо зафиксировать 3.9+ в проекте, либо использовать typing.Dict.
8. Глобальная зависимость review_service через импорт вместо DI FastAPI (app/api.py:30-37). Ухудшает тестируемость, жизненный цикл и подмену реализации. Рекомендация: использовать Depends с фабрикой зависимостей.

Низкая серьезность / стилистика
9. Промпт без контекстной структуры (app/review_service.py:20). Ответ LLM, скорее всего, будет неструктурирован. Рекомендация: просить структурированный вывод (список проблем с полями severity/file/line/message), чтобы API возвращало прогнозируемую схему.
10. Отсутствие логирования ключевых шагов и корреляции запросов (оба файла). Трудно отлаживать сбои LLM/валидатора.
11. Выбор POST без явного статуса 201/202 и без id ресурса (app/api.py:35-38). Если это «создание» ревью как ресурса — возможно, логичнее возвращать 201/объект с id или использовать 202 для асинхронной постановки в очередь.
12. Изменение сигнатуры Protocol на многострочную форму (app/review_service.py:10-13). Функционально ок, но шума в диффе больше; смысла немного.

Открытые вопросы
- Какой ожидается контракт ответа? Должны ли быть структурированные находки (severity, файл, строка, сообщение), а не один "comment"?
- Есть ли требования к аутентификации и лимитированию запросов к LLM?
- Какой максимальный размер diff допускается? Нужна ли обрезка/разбиение?
- Какой целевой runtime Python? 3.9+ допустим?
- Нужна ли асинхронная обработка и/или постановка задачи в очередь (например, если LLM работает долго)?

Краткие рекомендации по правке
- Ввести Pydantic-модели: ReviewRequest { diff: str }, ReviewResponse { comment: str } и указать response_model в маршруте.
- Валидировать наличие и тип поля diff, возвращать 422 при ошибках ввода.
- Обернуть вызов LLM в обработку ошибок, маппить таймауты/ошибки в предсказуемые ответы и логировать.
- Рассмотреть async-обработчик и run_in_threadpool либо асинхронный клиент LLM.
- Ограничить размер diff на входе и/или нормализовать его перед отправкой в LLM.
- Перевести импортированный singleton на Depends для лучшей тестируемости и расширяемости.
