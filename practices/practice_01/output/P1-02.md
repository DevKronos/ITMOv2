 ## Context Pack для первого рабочего сценария
 
 ### Факты и правила
 
 - 
 + Для одного PR помощник получает diff и возвращает: 1) краткое описание изменения; 2) не больше трёх рисков с файлом, строкой и доказательством; 3) список проверок, которые стоит запустить. Решение всегда принимает человек: помощник не может approve, merge или менять код.
 + Сервис предоставляет `POST /api/reviews`, ожидает поле `diff` в JSON и делегирует анализ LLM через `ReviewService.review()`.
 + `ReviewService.review()` формирует промпт вида `"Review this pull request and find problems:\n{diff}"` и возвращает результат как `{"comment": <строка>}`.
 + Для коммуникации предусмотрен эндпоинт здоровья `GET /health`.
 + Стиль комментариев ориентируем на примеры ниже.
 
 ### Формат входа и результата
 
 - 
 + Вход (задача помощника): текстовый `diff` одного PR.
 + Вход (API сервиса): JSON `{"diff": "<строка diff>"}`.
 + Ожидаемый результат (учебный кейс):
 +  1. краткое описание изменения;
 +  2. до трёх рисков с ссылкой на файл и строку и кратким доказательством;
 +  3. список проверок для запуска.
 + Фактический результат текущего сервиса: объект `{"comment": "<строка>"}` с ответом модели на промпт.
 
 ### Ограничения и запрещённые действия
 
 - 
 + Помощник не принимает решения: запрещены approve, merge и изменения кода.
 + Не более трёх рисков на PR.
 + Ссылаемся на конкретные файлы и строки, предлагаем воспроизводимые проверки.
 + Работать только с переданным `diff`; в тестовых запусках доступ к инструментам закрыт, контекст репозитория не используется.
 
 ### Хороший пример
 
 
 ```
 app/api.py, create_review — обращение payload["diff"] вызывает KeyError,
 если в теле запроса нет поля diff. Проверка: отправить POST /api/reviews
 с пустым JSON-объектом и проверить ответ сервиса.
 ```
 
 ### Плохой пример
 
 
 ```
 Код можно улучшить. Добавьте тесты и обработку ошибок.
 ```
 
 ### Что пока неизвестно
 
 - 
 + Целевой пользователь и среда использования за пределами учебного кейса (только ревьюеры курса или производственный сценарий?).
 + Требуемый контракт API результата: достаточно `{"comment": ...}` или нужен структурированный ответ с рисками и проверками (и как его вернуть в сервисе).
 + Требования к обработке ошибок и валидации входа (что возвращать при отсутствии `diff`).
 + Набор обязательных проверок, которые помощник должен рекомендовать (есть ли стандартный список).
 + Границы действий помощника в производственном режиме (доступ к репозиторию, инструментам, логированию).
