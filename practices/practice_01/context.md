## Context Pack для первого рабочего сценария

### Факты и правила

 - Для одного PR помощник получает diff и возвращает: 1) краткое описание изменения (summary); 2) не больше трёх рисков с полями `file`, `line`, `evidence`, `risk`; 3) список проверок (checks), которые стоит запустить. Решение всегда принимает человек: помощник не может approve, merge или менять код.
- Сервис предоставляет `POST /api/reviews`, ожидает поле `diff` в JSON и делегирует анализ LLM через `ReviewService.review()`.
- `ReviewService.review()` формирует промпт вида `"Review this pull request and find problems:\n{diff}"` и возвращает результат как `{"comment": <строка>}`.
- Для коммуникации предусмотрен эндпоинт здоровья `GET /health`.
- Стиль комментариев ориентируем на примеры ниже.

### Формат входа и результата

- Вход (задача помощника): текстовый `diff` одного PR.
- Вход (API сервиса): JSON `{"diff": "<строка diff>"}`.
 - Ожидаемый результат (целевой): JSON
   - `summary`: string — краткое описание изменения;
   - `risks`: array (max 3) of objects `{file: string, line: number, evidence: string, risk: string}`;
   - `checks`: array of strings — список проверок.
 - Фактический результат текущего сервиса: объект `{"comment": "<строка>"}` с ответом модели на промпт (расхождение с целевым форматом).

### Ограничения и запрещённые действия

- Помощник не принимает решения: запрещены approve, merge и изменения кода.
- Не более трёх рисков на PR.
- Ссылаемся на конкретные файлы и строки, предлагаем воспроизводимые проверки.
- Работать только с переданным `diff`; в тестовых запусках доступ к инструментам закрыт, контекст репозитория не используется.
 - Ограничения производительности: diff длиннее 20 000 символов отклоняется с HTTP 413.
 - Внешний вызов LLM: таймаут 10 секунд; ошибки преобразуются в контролируемый ответ (формат см. «Что пока неизвестно»).
 - Логирование: фиксируются только `request_id`, длительность и статус; содержимое diff и ответ модели не логируются.

### Хороший пример


```
app/api.py, create_review — обращение payload["diff"] вызывает KeyError,
если в теле запроса нет поля diff. Проверка: отправить POST /api/reviews
с пустым JSON-объектом и проверить ответ сервиса.
```

### Плохой пример


```
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Что пока неизвестно

 - Что возвращать при отсутствии поля `diff` или при неверном типе (код статуса и формат тела ошибки).
 - Формат контролируемого ответа при таймауте LLM или внутренних ошибках сервиса.
 - Требуется ли приводить API сервиса к целевому структурированному формату в рамках этой практики или это цель следующего инкремента.
 - Требования к аутентификации/авторизации и rate limiting для внешнего использования.

## Как использовали AI

- Для чего: собрать и зафиксировать AS IS-контекст и Context Pack по учебному кейсу, синхронизировать целевой формат ответа и ограничения сервиса по ответам студента, сохранить журнал промптов и результатов (P1-02).
- Тип промпта: инструкционный (редакторский) запрос к OpenCode на обновление артефактов по подтвержденным источникам.
- Строка в [`prompts.md`](prompts.md): P1-02 (запрос: «Первый промпт этой сессии», результат: practices/practice_01/output/P1-02.md).
- Что проверил студент и какие исправления поручил агенту: подтвердил целевого пользователя (разработчик, внешний сценарий), целевой контракт ответа (summary, risks[≤3]{file,line,evidence,risk}, checks), лимиты (diff > 20000 символов → HTTP 413; LLM timeout 10 секунд; без логирования содержимого), поручил обновить practices/practice_01/context.md, создать practices/practice_01/output/P1-02.md с промптами и ответами, и заполнить строку P1-02 в prompts.md; затем уточнил формат P1-02.md и агент переписал файл.
