# Integration-проверки

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Подтверждение |
|---|---|---|---|---|
| API (FastAPI) → ReviewService → LLM | Базовый сценарий не возвращает целевой структурированный ответ | Отправить `POST /api/reviews` с валидным JSON `{"diff": "<строка diff>"}` длиной ≤ 20 000; LLM отвечает быстро | HTTP 200 OK; тело содержит `summary: string`, `risks: array (≤3) of {file, line, evidence, risk}`, `checks: array of string` | `product_management.md` (позитивный сценарий); `adr.md` (Решение п.4); `analysis.md` (TO BE п.5) |
| API (FastAPI) вход → валидация | Отсутствует поле `diff` → неконтролируемая ошибка | Отправить `POST /api/reviews` с пустым `{}` | HTTP 4xx (контролируемая ошибка ввода); тело ошибки в согласованном формате (не определён сейчас) | `product_management.md` (ошибка без diff — 4xx); `adr.md` (Решение п.1); `analysis.md` (TO BE п.2) |
| API (FastAPI) вход → ограничение размера | Большой diff не отклоняется | Отправить `POST /api/reviews` с `diff` длиной > 20 000 символов | HTTP 413 Payload Too Large | `product_management.md` (413 при >20 000); `adr.md` (Решение п.2); `analysis.md` (TO BE п.3) |
| ReviewService → LLM (таймаут) | Долгий ответ LLM блокирует и не маппится в контролируемый ответ | Подменить LLM тестовым двойником, который спит >10 секунд; выполнить `POST /api/reviews` | Возврат контролируемого ответа об ошибке; время ответа ≤ 10 секунд | `product_management.md` (таймаут 10с → контролируемый ответ); `adr.md` (Решение п.3); `analysis.md` (TO BE п.4) |
| API → ReviewService (сквозной путь) | Неверная передача `diff` из API в сервис | Интеграционный запуск с тестовым `diff = "d"`; заинжектить тестовый ReviewService и проверить полученный аргумент | ReviewService получает ровно переданный `diff`; ответ API соответствует ответу сервиса | `TRAINING_PR.diff` (связка create_review → review), `analysis.md` (AS IS связь), `adr.md` (сквозной путь) |
| API → Логирование | В лог попадает содержимое `diff` или ответ модели; отсутствуют обязательные поля | Включить тестовый обработчик логов; выполнить `POST /api/reviews` с валидным diff | В логах присутствуют `request_id`, длительность и статус; отсутствуют фрагменты `diff` и содержимое ответа модели | `product_management.md` (не логировать содержимое); `adr.md` (Логирование п.5); `analysis.md` (TO BE логирование) |
| GET /health | Эндпоинт здоровья недоступен или возвращает неверное тело | Вызвать `GET /health` | HTTP 200 OK; тело `{"status": "ok"}` | `TRAINING_PR.diff` (реализация health); `analysis.md` (AS IS перечисление систем) |

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): будет добавлена после записи задачи про integration‑проверки.
- Что проверил студент и какие исправления поручил агенту: подтвердил связи компонентов (API ↔ ReviewService ↔ LLM), требования к валидации, лимиту 20 000 (413), таймауту 10с и логированию; поручил сформировать интеграционные сценарии без фиксации неоговорённых форматов ошибок (4xx/контролируемый ответ).
