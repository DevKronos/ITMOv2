# Проблема и метрики

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## Проблема

- Пользователь: разработчик, работающий с Git (внешний пользователь сервиса).
- Ситуация: оценивает изменения в PR по его diff и вызывает сервис `POST /api/reviews`, чтобы получить помощь в ревью.
- Что происходит сейчас: серверная часть напрямую обращается к `payload["diff"]` без валидации и делегирует анализ LLM, возвращая `{"comment": "..."}`. Это расходится с целевым контрактом ответа (нужны `summary`, `risks` ≤ 3 с `file,line,evidence,risk`, и `checks`). Риск `KeyError` и 500 при отсутствии поля `diff`. В коде отсутствует явная обработка таймаута LLM и ограничение размера diff (> 20 000 символов) на уровне API.
- Почему это мешает пользователю или бизнесу: нет структурированного ответа — сложно ссылаться на файл/строку и автоматизировать проверки; отсутствие валидации и обработок ошибок ведёт к нестабильным 5xx и непредсказуемому UX; невыполнение целевых ограничений (≤3 риска, 413 при большом diff, контролируемый ответ при таймауте) мешает надёжно интегрировать сервис во внешние процессы.
- Что не входит в задачу: принятие решений по PR (approve/merge) и изменения кода репозитория; доступ к инструментам и контексту репозитория вне переданного diff. Требования к аутентификации/авторизации и rate limiting в этом упражнении не определены.

## Метрики

Обсудите с OpenCode показатели, по которым можно проверить решение проблемы. Агент записывает согласованный способ замера и ожидаемое изменение для каждого показателя.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Соответствие структурному контракту ответа | Текущее: фактический ответ сервиса — `{"comment": "..."}`; замер — валидация ответа на структуру `summary/risks/checks` | 100% ответов соответствуют целевой структуре | После доработки API/логики и в интеграционных тестах | Ответы API `POST /api/reviews` |
| Обработка отсутствия поля diff | Текущее: риск `KeyError` и 500 при отсутствии `diff`; замер — отправить пустой JSON | 100% таких запросов возвращают контролируемую ошибку 4xx | В интеграционных тестах и при приемке | Ответы API, логи статусов |
| Ограничение размера diff | Текущее: требование — отклонять >20 000 символов; замер — отправить diff >20 000 | 100% таких запросов получают HTTP 413 | В интеграционных тестах | Ответы API |
| Таймаут LLM и контролируемый ответ | Текущее: в коде нет явной обработки; замер — симулировать таймаут LLM | 100% таймаутов маппятся в контролируемый ответ; клиент не ждёт >10 с | В тестах устойчивости и на приемке | Логи (длительность, статус), ответы API |
| Ограничение числа рисков | Текущее: сервис возвращает `comment`, соблюдение не проверяется; замер — валидировать поле `risks` | 100% ответов содержат не более 3 рисков | В интеграционных тестах | Ответы API / валидатор контракта |

## Почему изменение метрики подтвердит решение проблемы

Переход к структурированному контракту и его валидация устранят расхождение между целевым форматом и текущей реализацией, сделают результат пригодным для ссылок на файл/строку и автоматизации проверок. Контролируемые 4xx для отсутствующего `diff`, 413 для слишком длинного diff и обработка таймаутов в предсказуемые ответы снизят долю 5xx и стабилизируют UX внешних пользователей. Ограничение числа рисков обеспечит соответствие ожидаемому поведению помощника.
