# Анализ процесса: AS IS и TO BE

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## AS IS

Участники и системы:
- Внешний разработчик (пользователь сервиса), FastAPI-приложение (`app/api.py`), сервис ревью и LLM-протокол (`app/review_service.py`). Источник: `context.md`.

Процесс сейчас:
1. Пользователь отправляет `POST /api/reviews` с JSON `{"diff": "<строка diff>"}`. Источник: `context.md` (формат входа).
2. Обработчик `create_review(payload: dict)` напрямую обращается к `payload["diff"]` без проверки и передаёт строку в `ReviewService.review()`. Источник: `TRAINING_PR.diff`.
3. `ReviewService.review()` формирует промпт `"Review this pull request and find problems:\n{diff}"`, вызывает `llm.generate(prompt)` и возвращает `{"comment": answer}`. Источник: `TRAINING_PR.diff`, `context.md`.
4. Пользователь получает неструктурированный ответ `{"comment": "..."}`, который не соответствует целевому контракту `summary/risks/checks`. Источник: `context.md`.

Проблемы и задержки:
- Риск `KeyError` и 500 при отсутствии поля `diff` (нет валидации входа). Источник: `context.md`, `problem.md`.
- Нет ограничения размера входа: требование отклонять diff > 20 000 символов с 413 не реализовано. Источник: `context.md`, `problem.md`.
- Нет обработки таймаута LLM (10 секунд) и контролируемого ответа. Источник: `context.md`, `problem.md`.
- Контракт ответа неструктурирован (`{"comment": ...}`), что мешает ссылкам на файл/строку и проверкам. Источник: `context.md`, `problem.md`.
- Логирование не соответствует требованию (должны писаться только `request_id`, длительность, статус; содержимое не логируется). Источник: `context.md`.

## TO BE

Процесс после изменений (на основании результатов ревью P1-04 и согласованных ограничений в `context.md`/`problem.md`):
1. Получить запрос `POST /api/reviews`.
2. Валидация входа: проверить наличие поля `diff` и тип `string`. При отсутствии/неверном типе вернуть контролируемую ошибку 4xx (точный формат ошибки пока неизвестен — см. «Что пока неизвестно» в `context.md`).
3. Ограничение размера: если длина `diff` > 20 000 символов, вернуть HTTP 413.
4. Вызов LLM с таймаутом 10 секунд. При таймауте/ошибке — вернуть контролируемый ответ (формат уточняется).
5. Постобработка ответа: сформировать целевой структурированный результат `summary`, `risks` (не более 3, с `file,line,evidence,risk`), `checks`.
6. Вернуть успешный ответ и записать в лог только `request_id`, длительность и статус (без содержимого diff и ответа модели).

Диаграмма процесса:
```mermaid
flowchart LR
    A[POST /api/reviews] --> B{Есть diff и тип string?}
    B -- Нет --> E[4xx контролируемая ошибка]
    B -- Да --> C{len(diff) <= 20 000?}
    C -- Нет --> F[413 Payload Too Large]
    C -- Да --> D[LLM.generate с таймаутом 10s]
    D -- Ошибка/таймаут --> G[Контролируемый ответ об ошибке]
    D -- Успех --> H[Постпроцессинг: summary/risks<=3/checks]
    H --> I[200 OK структурированный ответ]
    E --> L[Лог: request_id, длительность, статус]
    F --> L
    G --> L
    I --> L
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Валидация входа `diff` | Доступ к `payload["diff"]` без проверок, возможен KeyError/500 | Проверка наличия и типа, контролируемая 4xx-ошибка при проблеме | Интеграционные тесты: пустой/неверный JSON → 4xx (см. `problem.md`) |
| Ограничение размера diff | Нет ограничений | Возвращать 413 при длине > 20 000 символов | Тест: отправить diff > 20 000, получить 413 (см. `problem.md`) |
| Таймаут и обработка ошибок LLM | Нет явной обработки, возможны долгие/непредсказуемые ответы | Таймаут 10 секунд, контролируемый ответ при таймауте/ошибке | Тест устойчивости: симулировать таймаут → контролируемый ответ ≤10с (см. `problem.md`) |
| Контракт ответа | `{"comment": "..."}` неструктурирован | Структурированный: `summary`, `risks` (≤3, с полями), `checks` | Валидация схемы ответа, интеграционные тесты (см. `problem.md`) |
| Логирование | Отсутствует/не определено | Логируются `request_id`, длительность, статус; не логировать diff/ответ | Проверка логов: наличие полей; отсутствие содержимого diff/ответа (см. `context.md`) |

## Как использовали AI

- Для чего: описать AS IS и TO BE процесса AI‑reviewer PR на основании `TRAINING_PR.diff`, `context.md`, `problem.md` и результатов ревью P1-04.
- Тип промпта: инструкционный (редакторский) запрос к OpenCode на формализацию процесса без домыслов вне подтвержденных источников.
- Строка в [`prompts.md`](prompts.md): P1-04 (ссылки на `output/P1-04.md`) — использованы находки для формирования TO BE.
- Что проверил студент и какие исправления поручил агенту: зафиксировал требования к входу, выходу, лимитам (413 > 20 000, таймаут 10 с), логированию и структурному контракту; поручил оформить процесс и различия с проверяемыми критериями.
