# Акции рядом: инструкции агенту

Небольшой локальный сервис на Python/FastAPI, SQLite и Jinja2: город, подписки,
реальные акции и уведомления внутри приложения. Сбор подключён только для ROSTIC’S.
Второй источник отложен. Не добавляй внешнюю доставку и пользовательские фильтры
без запроса.

## Карта проекта

- `app/source.py` — HTTP и разбор ROSTIC’S, исторические snapshots.
- `app/domain.py` — чистые правила сроков, территории, нормализации и хеширования.
- `app/storage.py` — SQLite, атомарный импорт и история уведомлений.
- `app/service.py` — подбор, preview, дедупликация и синхронизация; общую логику
  держи отдельно от HTTP и интерфейса; MCP использует тот же preview.
- `app/mcp_server.py`, `scripts/mcp_server.py` — stdio MCP и launcher;
  `scripts/prepare_mcp_demo.py` — отдельная offline-подготовка новой базы.
- `app/main.py`, `app/templates/`, `app/static/` — HTTP, фон и интерфейс.
- `app/cli.py` — импорт, sync, notify, preview; `tests/` — изолированные тесты.

## Работа и проверки

1. Прочитай `README.md` (условие лабораторной), `CONFIG.md`, актуальный код и
   затронутые тесты; перед правками проверь `git status`. Сохраняй чужие изменения.
2. Работай из каталога приложения. Активация не обязательна и в частично созданной
   venv может отсутствовать: используй `.venv/bin/python`,
   `.venv/bin/python -m pip`, `.venv/bin/python -m uvicorn app.main:app`.
   Зависимости ставь только в локальную venv по `CONFIG.md`, не глобально.
3. Единая проверка: `.venv/bin/python scripts/check.py`. Не ослабляй тесты.
   Тесты получают временные базы через `tests/conftest.py`.
   Для любых ручных тестов импорта, CLI и HTTP заранее задай `APP_DB_PATH`
   на новую базу во временном каталоге; для offline запуска — `APP_BACKGROUND=0`.
   Не используй рабочую `data/promos.db` как тестовую базу и не удаляй/сбрасывай её.
4. README с заданием не изменяй. Команды установки и запуска поддерживай в
   `CONFIG.md`; существенные новые подтверждения отмечай там же с датой,
   окружением, фактическими командами, результатом и ограничениями.
5. Отличай исторические snapshots от онлайн-сбора. Их успешный разбор не
   подтверждает доступ к сайту. Не меняй даты реальных акций ради демонстрации;
   проверяй срок на фиксированном timezone-aware времени в тестах.
6. Неизвестные сроки/территория не разрешают уведомление; отсутствие списка
   городов не означает общероссийское действие. Учитывай дни недели и Москву как
   часовой пояс. Частичный сбор импортирует успехи, но не скрывает прежние записи.
   Пометка отсутствия допустима только после полного подтверждённого каталога.
   Дедупликация: сеть + source_id + нормализованный город + версия содержимого;
   новое время получения само по себе не создаёт новое уведомление.
7. При ошибке или неожиданном поведении перед исправлением загрузи в OpenCode
   `skill({ name: "systematic-debugging" })`. Следуй четырём фазам: свидетельства,
   сравнение, проверка одной гипотезы, минимальное исправление и повторная проверка.
   Локальные адаптации и лицензия — в `.opencode/skills/systematic-debugging/SOURCE.md`.
   Для обычного чтения проекта без диагностики skill не обязателен.
8. Не выводи секреты, cookies и адреса прокси с учётными данными. Не обходи защиту
   источников и не отключай TLS. Различай sandbox и окружение серверного процесса.
9. Указывай только выполненные проверки: обнаружение skill не равно его загрузке,
   проверка Codex не равно запуску агента OpenCode. Повтор TestClient в одном
   процессе не называй перезапуском uvicorn. Не пиши reflection.md за студента;
   commit/push/публикация — только по отдельному запросу.
10. Проектный plugin `.opencode/plugins/python-check.js` автоматически проверяет
    успешные изменения Python в app/tests/scripts через edit/write/apply_patch.
    PASS приходит в результате инструмента. FAIL приходит как ошибка инструмента
    с кодом выхода и диагностикой; сама правка уже сохранена и не откатывается.
    Не повторяй исходную правку вслепую: она уже применена. При FAIL прочитай
    вывод, установи причину и исправь её, затем дождись новой
    проверки. Не скрывай FAIL и не объявляй работу завершённой по одному успешному
    редактированию. Отсутствующий Python и тайм-аут — тоже FAIL, а не пропуск.
    Изменения через bash/shell, внешние редакторы и custom/MCP tools hook не
    покрывает: после них запускай единую проверку отдельно и честно отмечай способ.
    Загрузка plugin требует нового запуска OpenCode; инструкции и ограничения
    демонстрации — в CONFIG.md. Пользователь предоставил вывод загрузки skill и
    автоматических FAIL/PASS hook; отличай эти сведения от проверок Codex.
11. Собственный MCP `discount_notifier` предоставляет только `preview_notifications`:
    город, подписки, checked_at, кандидаты и причины исключения из сохранённых данных.
    now необязателен, требует ISO 8601 с часовым поясом; остальные поля запрещены.
    Он не обновляет источник, не создаёт уведомления и не отправляет сообщения.
    APP_DB_PATH задаётся при запуске, не аргументом tool; проектная конфигурация
    направлена на отдельную `.opencode/demo/promos.db`, не рабочую базу.
    Для строгого чтения без WAL/SHM-записей используйте подготовленную неактивную
    базу без других писателей. Наличие WAL вызывает ошибку; не удаляйте его вручную.
    Подготовка и ограничения — в CONFIG.md. При isError прочитайте причину и
    исправьте аргументы/подготовку; не выдавайте ошибку за пустой успешный preview.
    Codex проверил stdio-клиент отдельно. По сведениям пользователя OpenCode
    выполнил успешный MCP-вызов; ошибочный агентный вызов ещё не проверялся.
